# advisor — 对局助手（PyQt6 + 本地识别 + LLM）

把现有脚本串成一条**固定工作流**：一张截图 → 识别 → 规则推荐 → 数据补充 → LLM 教练，
两个标签页分别回答「现在该干什么」和「机器到底读到了什么」。

```
截图 ──scan.py──▶ 局面 JSON ──comp_match/economy──▶ 候选阵容 + 行动
                        │                                │
                        │                                ├─ s18db 补充：站位/过渡/装备/符文/阵容码
                        └──────────┬─────────────────────┘
                                   ▼
                          LLM（qwen-flash）润色 + 排序
                                   ▼
                    Tab1 阵容推荐        Tab2 识别标注
```

不改 `core/`、`scan.py`、`recommend.py` 的任何行为，只做编排与展示。

## 运行

```bash
python -m pip install PyQt6            # 只在没装时
python advisor/app.py                  # 打开界面，点「打开截图」或把图拖进窗口
python advisor/app.py 图.png            # 带图启动
python advisor/app.py 图.png --shot out.png   # 自检：渲染两个标签页截图后退出
python advisor/pipeline.py 图.png       # 只跑流水线，命令行看结果（--no-llm 关掉 LLM）
```

依赖与 `scan.py` 相同（numpy / scipy / Pillow / rapidocr-onnxruntime），LLM 复用
`core/vlm_board_scan.py` 的百炼 key，也可用 `DASHSCOPE_API_KEY` 覆盖。

## 两个标签页

### Tab1 · 阵容推荐

一页**教练式文本**，不是卡片墙。除了「变阵」单独加框强调，其它都是带主色竖线的段落。

```
日蚀骑士韦鲁斯 [S]   均名 4.36 · 前四 53.0%              [复制阵容码]
打法  [#1 日蚀骑士韦鲁斯·S]  [#2 重装战士凯特琳·B]  [#3 峡谷野怪峰喙鸟·S]
为什么是这套：你手上已经有 瑟庄妮（主坦）、蕾欧娜、洛；DD街区 提供免费刷新，正好配这套
              慢 D 打法；手上的 锁子甲+负极斗篷 能直接合出它的 石像鬼石板甲（给瑟庄妮）。
教练（qwen-flash）：当前经济良好，可稳血过渡…

★ 变阵（最该记住的一条） → 什么时候转 / 转去哪套 / 留着谁 / 到时候卖谁（回收多少金）/ 去找谁
▍强化符文           → 只放图标，悬停才出评级、描述、契合点
▍站位               → 4×7 六边形棋盘常显：头像 / 角色·名字+星级 / 三件推荐装备，
                      主C=红、副C=蓝、主坦=绿，装备描金边=核心装，
                      绿框=已有，悬停看完整装备名
▸ 识别信息 / 告警     → 耗时、字段来源、识别告警（默认收起）
```

一屏放得下，不用滚动。

**刻意不显示**：血量、金币、等级这类游戏里自己就能看到的数字（只在需要解释决策时出现在句子里）；
商店 5 格逐条「买/不买」；阵容机制长篇介绍；每个字段的来源标记（收进折叠区）。

界面上的结论都是算出来的：

| 结论 | 算法 |
|---|---|
| 「变阵去哪套 / 留谁 / 卖谁回收多少」 | 遍历其它候选，按「已拥有单位的重叠度」选；回收 = 单价 ×（2★ 按 3 张算） |
| 「某英雄的核心装是哪件」 | `databook.rank_build()`：成型棋盘 `board.equips` / 本阵容 `equipOptions[0]` / `recommendedEquips` / `roleRecommendedEquips` 四个来源各按「第 1/2/3 位」计分，取最高；可在 `config/equip_core.json` 人工钉死 |

**为什么不把所有东西都交给 LLM**：这些数字要可复现、可解释，LLM 只额外给一句
「本局判断 / 该不该搜」，并且这一句在界面上明确标了来源（`教练（qwen-flash）`），
关掉「LLM 建议」后其它内容一个字都不会变。

### Tab2 · 识别标注

- 原图叠加每个识别结果的框：文本字段（阶段/等级/经验/金币）、商店 5 格、棋盘与备战席单位
  （含装备格）、羁绊行、装备栏、强化符文图标、8 名玩家的血量行。
- 框的颜色按分组区分，标签常显；顶部可按分组开关，也可以关闭标签只看框。
- 右侧树表逐项列出「识别项 / 取值 / 来源（ocr·cv·vlm·label）」，点条目 → 图上高亮，点图 → 树表跳转。
- 滚轮缩放、拖拽平移、双击复位。

## 响应时间（≤10s 怎么保证的）

| 环节 | 典型 | 上限控制 |
|---|---|---|
| 识别 `scan(backend=ocr, labels)` | 2.3s（CLI）/ 4~8s（GUI 抢占 CPU 时） | 不加 VLM 回落就不会慢 |
| 规则推荐 + 数据补充 | 0.03s | 纯内存计算 |
| LLM `qwen-flash` | 0.7~2.0s | **墙钟硬超时 3.5s**，超时立刻回落规则文案 |
| 合计 | **3.4~6s** | 最坏 ≈ 识别耗时 + 3.5s |

三个加速手段：

1. **启动即预热**（`pipeline.warm()`，后台线程）：OCR 模型 0.9s、棋子/装备模板 0.9s、
   符文形状掩膜 0.6s、静态 JSON 0.02s —— 用户选图的时间把这些先付掉。
2. **结果缓存**：`output/advisor_cache/<图片内容哈希>.json`，同一张图再打开 < 0.1s；
   「重新分析」会绕过缓存并刷新它。缓存 key 含后端与是否启用 LLM。
3. **LLM 不阻塞 UI**：整个链路在 QThread 里跑，LLM 再套一层子线程做硬 deadline，
   失败/超时/JSON 不合法都只影响文案，不影响识别与规则结果。

## LLM 用在哪、怎么防幻觉

只做「语言」不做「事实」：

- 输入是压缩后的局面 + 主推阵容 + 规则行动 + **符文候选名单**；
- 输出被 `llm._validate()` 钉死：符文名必须在候选池里，牌名必须在「已有/还缺」里，
  越界的条目直接丢弃（界面上不会出现编造的英雄或符文）；模型如果把字段说明
  （「40字内」这类）当成结论抄回来，也会被判为无效并回落规则文案；
- 装备建议**不交给 LLM**，完全由 `items.json` 的合成配方 + 阵容 `equipOptions` 确定性算出，
  保证「锁子甲+负极斗篷=石像鬼石板甲」这类结论不会错。

模型/超时可用环境变量覆盖：`JCC_LLM_MODEL`（默认 `qwen-flash`）、`JCC_LLM_TIMEOUT`（默认 `3.5`）。

## 文件

| 文件 | 职责 |
|---|---|
| `advisor/app.py` | PyQt6 界面：两根标签页、段落排版、站位棋盘、标注画布、线程与缓存 |
| `advisor/pipeline.py` | 工作流编排：`warm()` / `analyze()` / 标注几何生成 / 符文候选初筛 |
| `advisor/plan.py` | 把局面 + 推荐 + 静态库压成几段「人话」（拿牌/节奏/升级/变阵/装备），所有数字现算 |
| `advisor/databook.py` | `data/` 与 `data/s18db/` 只读访问：阵容详情、装备配方、图标、概率与经验表 |
| `advisor/llm.py` | 百炼 OpenAI 兼容接口、硬超时、输出校验、规则回落文案 |

## 已知限制

- 识别能力的限制就是 `scan.py` 的限制：只支持 16:9 附近；别在战斗阶段截图。
- 阵容模板与符文评级来自 `data/s18db/`，站点数据不更新时建议会变旧（重建见 `docs/s18db.md`）。
- **核心装是推断出来的，不是数据字段**：`rank_build()` 用四个来源投票，机制型核心（凯尔/凯特琳的羊刀、
  厄斐琉斯的羊刀）已写进 `config/equip_core.json` 保底；数据自身打架的英雄（例如韦鲁斯的
  `board` 首位是朔极之矛、`recommendedEquips` 首位是无尽之刃）需要你自己在配置里钉死。
- 「站位推荐」画的是模板给的理想站位，不会因为你场上单位不同而重排；每格下方的三件装备来自站点的成型盘，顺序由 `rank_build` 排（核心装描金边）。主C/副C/主坦由 `_role_map()` 判定：主C = 站点 `mainHeroName`，主坦 = 装备方案里第一个两件以上肉装的英雄，其余有装备的算副C。
- 符文候选的排序是「评级 + 与阵容的字面契合」，不是真实胜率；`s18db` 里没有按阵容维度的符文统计。
- 阵容码（`jccCode`）来自站点导出，复制到游戏里的可用性随版本变化。
- 装备「下一件抢什么」只考虑散件配方，不知道对手拿了什么、也不预测野怪会爆哪几件。
